# תכנון רכיב המסחר האמיתי (שלב ב'): מסמך תכנון בלבד

מסמך זה מתאר מה יידרש כדי להעביר את המערכת ממצב סימולציה למסחר אמיתי בחשבון
Kraken. הוא אינו מפעיל דבר. בגרסה הנוכחית מצב live חסום בקוד, אין מפתחות API,
והמערכת ממשיכה לרוץ בסימולציה בלבד. הביצוע בפועל של כל שלב במסמך ייעשה רק
בהחלטה מפורשת של בעל החשבון.

העובדות על ממשק Kraken במסמך זה אומתו מול התיעוד הרשמי ב-12 בנובמבר 2026
(docs.kraken.com ו-support.kraken.com). פרט שלא אומת מסומן במפורש.

## 1. עקרונות

1. הרשאות מינימום. מפתח ה-API יקבל רק את ההרשאות הנדרשות למסחר ולצפייה ביתרה.
   לעולם לא הרשאת משיכה, הפקדה, ייצוא נתונים או ניהול.
2. כסף נפרד ומוגבל. הבוט יפעל רק על סכום שהוגדר מראש כסכום שניתן להפסיד במלואו,
   ובנוסף לאחוזי המגבלות תוגדר תקרה מוחלטת בדולרים.
3. סודות בקובץ .env בלבד. המפתח והסוד מוקלדים לקובץ על ידי בעל החשבון בלבד,
   לא נשלחים בשיחה, לא נרשמים ליומן, לא מודפסים למסך, ולא עולים למאגר.
4. אין שינוי במבנה. הרכיב LiveExecutor מחליף את SimulatedExecutor בלבד. הסורק,
   הבודק, ניהול הסיכון, היומן והאסטרטגיה נשארים כפי שהם.
5. כל מעבר בין שלבים דורש הרצה מוצלחת של כל הבדיקות ואישור של בעל החשבון.

## 2. מה אומת מול התיעוד של Kraken

### 2.1 אימות בקשות לנקודות קצה פרטיות

כתובת הבסיס: https://api.kraken.com/0. נקודות הקצה הפרטיות נמצאות תחת /0/private.

כל בקשה פרטית נשלחת ב-POST עם שתי כותרות: API-Key (המפתח הציבורי) ו-API-Sign
(החתימה). בגוף הבקשה חובה שדה nonce, מספר שלם חיובי של 64 ביט שעולה תמיד
(הנוהג המקובל: חותמת זמן UNIX במילישניות). אין דרך לאפס nonce למטה, ו-nonce לא
תקין עלול לגרום לחסימה זמנית. ביצירת המפתח ניתן להגדיר "Custom Nonce Window"
לסובלנות של שנייה עד עשר שניות.

חישוב החתימה, כלשון התיעוד: HMAC-SHA512 של (נתיב ה-URI + SHA256(nonce + נתוני
ה-POST)), כשהמפתח ל-HMAC הוא הסוד לאחר פענוח base64, והתוצאה מקודדת ב-base64.
נתיב ה-URI לחתימה מתחיל ב-/0/private, למשל /0/private/AddOrder. בתיעוד קיים וקטור
בדיקה (מפתח לדוגמה וערך חתימה צפוי), והבדיקות שלנו ישתמשו בו כדי לוודא שהחתימה
מחושבת נכון עוד לפני כל פנייה לשרת.

### 2.2 הזמנה: AddOrder

נתיב: POST /0/private/AddOrder. שדות חובה: nonce, pair, type, ordertype, volume.

למסדר קנייה בשוק: ordertype = market, type = buy, pair = מזהה הזוג או ה-altname
(למשל XBTUSD), volume = כמות ביחידות הנכס הנקנה, כמחרוזת. למכירה: type = sell.

שני פרמטרים חשובים לתכנון:

- validate = true: ההזמנה נבדקת בלבד ואינה נשלחת למנוע המסחר. זהו הבסיס לשלב
  "הרצה יבשה" (סעיף 5, שלב 2).
- oflags = viqc: הכמות מבוטאת במטבע הציטוט (דולר) במקום ביחידות הנכס. נתמך רק
  בהזמנות קנייה בשוק. מאפשר לשלוח "קנה ב-49 דולר" במקום לחשב כמות ולהתמודד עם
  עיגול, ולכן זהו הנתיב המועדף לקנייה.

תשובה: result מכיל descr (תיאור ההזמנה) ו-txid (מערך מזהי הזמנה). השדה error הוא
מערך, ריק בהצלחה. התשובה אינה מכילה את פרטי המילוי (מחיר בפועל, עמלה). לשם כך
נדרשת שאילתה נפרדת (סעיף 2.3).

### 2.3 יתרה ומצב הזמנות

יתרה: POST /0/private/Balance, דורש nonce בלבד. מחזיר מפה של קוד נכס ליתרה
כמחרוזת (למשל ZUSD, XXBT). יש להמיר קודים פנימיים לשמות מוכרים, כפי שכבר נעשה
בפונקציה normalize_asset. התיעוד מזכיר נקודת קצה BalanceEx עם שדה החזקה
(hold_trading); היא לא נקראה ולא אומתה.

מצב הזמנה: QueryOrders (הרשאות "Query Open Orders & Trades" ו-"Query Closed
Orders & Trades"). דף התיעוד של נקודת קצה זו החזיר שגיאה 404 בעת האימות, ולכן
שמות השדות של סטטוס, כמות שבוצעה, מחיר ממוצע ועמלה לא אומתו ואינם מופיעים כאן.
יש לאמת אותם מול התיעוד לפני כתיבת הקוד.

### 2.4 מגבלות קצב

לכל מפתח מונה קריאות. רוב הקריאות הפרטיות מעלות את המונה ב-1, קריאות להיסטוריה
(ledger, trades) ב-2. AddOrder ו-CancelOrder פועלות תחת מגבלה נפרדת שפרטיה לא
מופיעים בדף שנקרא. המונה המרבי והדעיכה תלויים בדרגת החשבון: Starter 15 ודעיכה
0.33 לשנייה, Intermediate 20 ו-0.5 לשנייה, Pro 20 ו-1 לשנייה. חריגה מחזירה
EAPI:Rate limit exceeded. הסריקה הנוכחית משתמשת רק בנקודות קצה ציבוריות ואינה
נספרת במונה זה.

### 2.5 הרשאות מפתח API

לפי דף התמיכה, ההרשאות מחולקות לקבוצות:

- Funds: Query Funds, Deposit Funds, Withdraw Funds.
- Orders & Trades: Query Open Orders & Trades, Query Closed Orders & Trades,
  Modify Orders (כולל AddOrder), Cancel/Close Orders.
- Data: Query Ledger Entries, Export Data.

הגדרות נוספות במסך היצירה: IP Address Restriction (הגבלת כתובת IP), Key
Expiration (תפוגה, למשל שבוע), Query Start/End Date/Time, Custom Nonce Window,
ואפשרות ל-2FA על המפתח עצמו (ואז כל בקשה דורשת שדה otp).

הערה: דפי ה-docs מנסחים את שמות ההרשאות מעט אחרת מדף התמיכה (למשל "Create &
modify orders" מול "Modify Orders"). יש לוודא את השם המדויק במסך יצירת המפתח.

| הרשאה | נדרשת | סיבה |

| Query Funds | כן | קריאת היתרה בכל סבב |
| Query Open Orders & Trades | כן | מעקב אחר הזמנה שנשלחה |
| Query Closed Orders & Trades | כן | קריאת המילוי בפועל: מחיר, כמות, עמלה |
| Modify Orders | כן | שליחת הזמנות קנייה ומכירה |
| Cancel/Close Orders | כן | ביטול הזמנה שלא מולאה |
| Withdraw Funds | לא, בשום מקרה | |
| Deposit Funds | לא | |
| Query Ledger Entries | לא | |
| Export Data | לא | |

הגדרות מומלצות במסך היצירה: הגבלת IP לכתובת המחשב שעליו הבוט רץ, תפוגה קצרה
(לחדש במקום להשאיר מפתח קבוע), ושם ברור למפתח. 2FA על המפתח עצמו אינו מתאים
לבוט אוטומטי, כי הוא דורש קוד חד-פעמי בכל בקשה.

## 4. מה ייבנה בקוד

### 4.1 לקוח פרטי: app/kraken.py

הרחבת הקובץ הקיים במחלקה KrakenPrivateClient, עם:

- פונקציית חתימה טהורה (ללא רשת) שמקבלת נתיב, nonce, נתוני POST וסוד, ומחזירה
  API-Sign. נבדקת מול וקטור הבדיקה שבתיעוד.
- מחולל nonce עולה: חותמת זמן במילישניות, עם הבטחה שכל ערך גדול מהקודם גם אם
  שתי בקשות נשלחות באותה מילישנייה.
- פונקציות: balance, add_order (עם תמיכה ב-validate וב-viqc), query_orders,
  cancel_order.
- מונה קצב מקומי לפי דרגת החשבון (הגדרה חדשה KRAKEN_TIER, ברירת מחדל Starter,
  המגבלה המחמירה ביותר), עם השהיה לפני חריגה.
- הסוד נשמר בזיכרון בלבד, לעולם לא ב-repr, ביומן או בהודעת שגיאה. בדיקה ייעודית
  תוודא שהסוד אינו מופיע בשום הודעת חריגה.

### 4.2 מבצע אמיתי: app/executor.py

המחלקה LiveExecutor תממש את אותו ממשק Executor (buy, sell) ותחזיר Fill, כך שהבוט
לא ישתנה. תהליך קנייה:

1. בדיקת מינימום הזמנה (ordermin, costmin) כפי שכבר נעשה בסימולציה.
2. שליחת AddOrder בשוק עם oflags = viqc וסכום בדולרים.
3. קבלת txid, ואז שאילתת QueryOrders עד שההזמנה סגורה או עד תום זמן קצוב.
4. בניית Fill מהמילוי בפועל: כמות שבוצעה, מחיר ממוצע, עמלה. simulated = False.
5. אם ההזמנה לא נסגרה בזמן הקצוב: ביטול, קריאה חוזרת של המצב, ואם מולאה חלקית,
   רישום הכמות שבוצעה כפוזיציה (ראו 4.4).

מכירה: AddOrder בשוק עם type = sell ו-volume בכמות הנכס, ואותו מעקב מילוי.

הפעלה ב"הרצה יבשה": דגל LIVE_VALIDATE_ONLY=true יגרום לכל AddOrder להישלח עם
validate = true. ההזמנה נבדקת על ידי Kraken (זוג, כמות, מינימום) אך אינה
מבוצעת, והבוט ממשיך לנהל את הפוזיציה כבסימולציה.

### 4.3 אימות בהפעלה: app/main.py ו-app/config.py

כאשר MODE=live, לפני הפעלת הלולאה:

1. בדיקה שהמפתח והסוד אינם ריקים.
2. קריאת Balance כבדיקת חיבור. כשל עוצר את ההפעלה.
3. שליחת AddOrder עם validate = true על זוג נזיל בכמות מינימלית, כדי לוודא שיש
   הרשאת מסחר. כשל עוצר את ההפעלה.
4. בדיקה שלילית: ניסיון קריאה לנקודת קצה שדורשת הרשאת משיכה (למשל WithdrawInfo
   עם פרמטרים לא תקפים). אם הקריאה אינה נדחית בשגיאת הרשאה, המפתח רחב מדי
   והמערכת מסרבת לרוץ. אופן הבדיקה המדויק ייקבע לאחר אימות התנהגות נקודת הקצה.
5. הדפסת סיכום ללא ערכי המפתח: דרגת חשבון, יתרה זמינה, תקרה מוחלטת, מצב הרצה
   יבשה.

הגדרות חדשות בקובץ .env:

| הגדרה | משמעות | ברירת מחדל |
|---|---|---|
| LIVE_MAX_TOTAL_USD | תקרה מוחלטת בדולרים לסך הפוזיציות הפתוחות | 0 (חוסם מסחר עד שנקבע ערך) |
| LIVE_VALIDATE_ONLY | הרצה יבשה: הזמנות נבדקות ואינן מבוצעות | true |
| LIVE_CONFIRM | מחרוזת אישור שחובה להקליד כדי לאפשר live | ריק (חוסם) |
| KRAKEN_TIER | דרגת החשבון לצורך מגבלת קצב | starter |
| ORDER_TIMEOUT_SECONDS | זמן המתנה למילוי לפני ביטול | 30 |

מצב live יופעל רק כששלושת התנאים מתקיימים יחד: MODE=live, LIVE_CONFIRM מכיל את
המחרוזת המדויקת שתוגדר בקוד, ו-LIVE_MAX_TOTAL_USD גדול מאפס.

### 4.4 סנכרון יתרה ופוזיציות: app/bot.py

- במצב live, המזומן אינו נשמר במצב הפנימי אלא נקרא מ-Balance בכל סבב (מטבע
  הציטוט). ההון מחושב מהיתרה בפועל ועוד שווי הפוזיציות.
- בהפעלה, השוואה בין הפוזיציות הפתוחות ביומן לבין האחזקות בחשבון. פער (נכס
  שקיים בחשבון ולא ביומן, או להפך) נרשם כאירוע ברמת error והמערכת עוברת להשהיה
  עד להחלטה ידנית. הבוט לעולם לא מוכר נכס שלא הוא קנה.
- מילוי חלקי: הפוזיציה נרשמת ביומן בכמות שבוצעה בפועל ובעלות בפועל, ולא בסכום
  שתוכנן. השדה qty ביומן הוא תמיד הכמות שבוצעה.
- כשל במכירה (למשל שגיאת רשת אחרי שליחה): לפני ניסיון חוזר, שאילתת מצב ההזמנה
  לפי txid, כדי לא למכור פעמיים.
- עצירת החירום הקיימת נשארת. במצב live, סגירת כל הפוזיציות בעצירה היא פעולה
  אמיתית, ולכן תירשם ביומן לפני הביצוע ואחריו.

### 4.5 בדיקות: tests/

ללא רשת, כמו היום:

- חתימה: וקטור הבדיקה מהתיעוד.
- nonce עולה גם בקריאות צפופות.
- הסוד אינו מופיע בשום הודעת שגיאה או ביומן.
- LiveExecutor עם לקוח מדומה: מילוי מלא, מילוי חלקי, ביטול אחרי זמן קצוב,
  הזמנה שנדחתה.
- חסימה: MODE=live ללא LIVE_CONFIRM או עם תקרה אפס אינו מפעיל מסחר.
- סנכרון: פער בין יומן לחשבון מוביל להשהיה.
- תקרה מוחלטת: ניסיון לחרוג ממנה נחסם לפני השליחה.

## 5. שלבי מעבר, כל אחד באישור נפרד

1. בניית הקוד לפי סעיף 4, עם כל הבדיקות עוברות. MODE נשאר simulation. המפתח
   עדיין לא נוצר.
2. יצירת מפתח לפי סעיף 3, הקלדתו לקובץ .env על ידי בעל החשבון, והרצה יבשה:
   MODE=live עם LIVE_VALIDATE_ONLY=true. כל הזמנה נבדקת על ידי Kraken ואינה
   מבוצעת. שלב זה מאמת חיבור, הרשאות, חתימה ומינימום הזמנה, ללא סיכון כספי.
   משך מומלץ: לפחות כמה ימים.
3. הורדת המגבלות הקשיחות לערכים המתאימים לכסף אמיתי. זהו שינוי במגבלות ולכן
   ייעשה רק בהחלטה מפורשת. ערכים מקובלים להתחלה הם חד-ספרתיים, הן להפסד היומי
   והן לגודל הפוזיציה.
4. הפעלה עם סכום קטן: LIVE_VALIDATE_ONLY=false, LIVE_MAX_TOTAL_USD בסכום נמוך
   שהוגדר מראש, ויתרה בחשבון שאינה עולה בהרבה על סכום זה.
5. הגדלה הדרגתית רק לאחר תקופה מתועדת ללא תקלות תפעוליות (מילויים חלקיים,
   פערי סנכרון, שגיאות קצב).

## 6. סיכונים שאינם בקוד

- תוצאות הסימולציה אינן מנבאות תוצאות אמיתיות. הסימולציה מניחה מילוי במחיר
  ask או bid עם סליפג' קבוע. בשוק אמיתי, בזוגות דלילים, המילוי עלול להיות גרוע
  בהרבה, במיוחד בהזמנות שוק בזמן קפיצת נפח.
- עמלות בפועל תלויות בדרגת החשבון ובהיקף המסחר, ועשויות להיות שונות מהמדרגה
  הראשונה שהסימולציה מניחה.
- Kraken עשויה לשנות את הממשק, את ההרשאות או את מגבלות הקצב. כל שלב ייבדק
  מחדש מול התיעוד העדכני.
- אחריות: המערכת היא כלי לימודי. מסחר בקריפטו כרוך בסיכון להפסד מלא של הכסף.
